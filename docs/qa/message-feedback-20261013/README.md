# 消息状态展示与发送幂等

## 行为

- 普通成功发送、completed 不显示常驻状态；无需回复、有 run 的未关联回复、处理中与失败保留明确说明。
- API 为 reply_activity 增加 `basis: run | legacy`。仅隐藏 legacy unconfirmed；不回填或重放历史数据。
- unconfirmed 无重试。其他用户只看到等待/处理中；发送者能看到异常及重试风险。
- 点击重试时读取 store 最新状态，已完成/无需回复的 agent 不再被选中。
- 同一 HTTP 发送的网络重试保留 `client_request_id`。明确要求 agent 再执行的请求生成新键；新请求若网络失败，从新气泡继续复用该键。

## 幂等范围

`POST /api/dashboard/rooms/{room_id}/send` 接收可选 client_request_id（1–128 个字母/数字/下划线/连字符）；新房间消息 composer 路径总是传入。旧客户端和未提供键的调用继续保留旧行为，不在幂等保证内。

服务端用 `(user_id, sender_id, room_id, client_request_id)` 的 SHA-256 作为持久化主键；请求内容摘要用于拒绝同键不同内容（409）。唯一插入在数据库层串行化同键并发请求，预留记录、topic 计数和消息扇出在同一事务提交。已提交请求返回原响应，不重复发送通知。权限和房间成员资格仍会检查。

这保证同一个已接受的发送请求不重复创建消息/扇出，不保证 agent 工具恰好执行一次。执行中断、投递租约重试以及用户明确再次执行仍可能产生重复副作用，需要 daemon 与具体工具另外实现幂等。客户端警告只说明风险。

幂等记录不设置短期过期时间：若先删除键，迟到的重试可能重新发送。删除或保留策略须与消息保留策略一起设计；本次不自动清理线上数据。
